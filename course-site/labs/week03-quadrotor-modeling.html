Quadrotor Modeling — thrust, torque & the X-frame mixer

Build the mixing matrix by hand, invert it, and prove a hover allocates four equal motor thrusts.

← Back to the Week 3 slides Course home

Goal Construct the X-frame mixing matrix \( \mathbf{M} \) that maps 4 motor thrusts → the control wrench \([T,\tau_x,\tau_y,\tau_z]\), invert it to get the allocation, and verify two things: a pure-hover wrench \([mg,0,0,0]\) allocates to four equal motor thrusts \(mg/4\), and the round-trip wrench → motors → wrench returns the original. This is the actuator model every later controller relies on.

1 · The 5-minute recap

Each rotor makes thrust along +body-z, quadratic in speed \( f_i = k_f\,\omega_i^2 \), plus a reaction drag torque about z that alternates sign — two rotors spin CW, two CCW — so it cancels at hover and the residual gives yaw control. We model each motor directly by its thrust \(f_i\) [N]; the yaw torque is \( \pm c\,f_i \) with \( c=\)k_torque.

The course is X-frame: every arm sits at 45° to the body axes, so every motor has a moment arm on both roll and pitch. With arm \(l\) and torque ratio \(c\):

\[ \begin{bmatrix}T\\\tau_x\\\tau_y\\\tau_z\end{bmatrix}= \underbrace{\begin{bmatrix}1&1&1&1\\-l&-l&l&l\\ l&-l&-l&l\\-c&c&-c&c\end{bmatrix}}_{\mathbf{M}} \begin{bmatrix}f_1\\f_2\\f_3\\f_4\end{bmatrix} \]

Convention hazard — read before you code Most free references (MathWorks NMPC, Bresciani, Gibiansky) print the plus-frame matrix, where roll uses only motors 2&4 and pitch only 1&3. That is a different airframe. If you copy it, your roll and pitch will be wrong. Use the X-frame \(\mathbf{M}\) above — it matches quadsim.params.mixer_matrix(). See simulator/CONVENTIONS.md.

3 · Build & invert the mixer

Work through the steps. You'll write everything into one script, examples/wk3_mixer.py. Recall the wrench layout: u[0] total thrust \(T\), u[1:4] body torques \((\tau_x,\tau_y,\tau_z)\).

1 Per-motor hover thrust start here

At a level hover the four motors share the weight equally. Total thrust must equal \(mg\), so each motor carries \(mg/4\):

import numpy as np
from quadsim import QuadParams

p = QuadParams()
hover_total      = p.weight                 # = mass * g  [N]
hover_per_motor  = hover_total / p.n_rotors # = mg / 4    [N]
print(hover_per_motor)                      # -> 1.594...  (≈ mg/4)

QuadParams also exposes p.hover_thrust_per_motor — use it to cross-check your number.

2 Build the X-frame mixer \( \mathbf{M} \) by hand the core

Type the matrix out from the equation above, using \(l=\)p.arm and \(c=\)p.k_torque. Do not copy a plus-frame matrix — every torque row must have a nonzero entry for all four motors.

l, c = p.arm, p.k_torque
M = np.array([
    [ 1.0,  1.0,  1.0,  1.0],   # T     : sum of thrusts
    [  -l,   -l,    l,    l],    # tau_x : roll  — all four contribute
    [   l,   -l,   -l,    l],    # tau_y : pitch — all four contribute
    [  -c,    c,   -c,    c],    # tau_z : yaw   — CW/CCW pattern
])
print(np.allclose(M, p.mixer_matrix()))     # -> True (matches quadsim)
3 Invert it → the allocation matrix wrench → motors

The controller speaks in wrench; the motors need thrusts. Invert \(\mathbf{M}\). It is invertible by construction:

M_inv = np.linalg.inv(M)
print(np.allclose(M_inv, p.allocation_matrix()))   # -> True

In production quadsim calls p.allocation_matrix(), which is exactly this inverse.

4 Hover-allocation check graded ⭐

Feed a pure-hover wrench (thrust only, zero torque) through the allocation. It must split into four equal motor thrusts \(mg/4\):

u_hover = np.array([p.weight, 0.0, 0.0, 0.0])
f_hover = M_inv @ u_hover
print(f_hover.round(4))                              # -> [1.594 1.594 1.594 1.594]
print(np.allclose(f_hover, p.weight / 4))            # -> True

If the four numbers aren't equal, a sign in \(\mathbf{M}\) is wrong (most likely a torque row).

5 Round-trip check + saturation verify

Compare your hand-built map against quadsim's, and confirm wrench → motors → wrench returns the original when nothing saturates. wrench_to_motor_forces clips each \(f_i\) to \([f_{\min},f_{\max}]\):

from quadsim.dynamics import wrench_to_motor_forces, motor_forces_to_wrench

f = wrench_to_motor_forces(u_hover, p)               # allocation @ u, then clip
u_back = motor_forces_to_wrench(f, p)                # mixer @ f
print(np.allclose(u_back, u_hover))                  # -> True (unsaturated round-trip)

# Now over-drive yaw so a motor clips at f_max = 4 N and the round-trip BREAKS:
u_big = np.array([p.weight, 0.0, 0.0, 5.0])
f_clip = wrench_to_motor_forces(u_big, p)            # some f_i pinned at f_max
print(np.allclose(motor_forces_to_wrench(f_clip, p), u_big))  # -> False
✓ Stuck? Reveal the full wk3_mixer.py
Try first You learn the model by typing the matrix out and watching the round-trip. Peek only after a genuine attempt.
# examples/wk3_mixer.py — Week 3: build & invert the X-frame mixer
import numpy as np
from quadsim import QuadParams
from quadsim.dynamics import wrench_to_motor_forces, motor_forces_to_wrench

p = QuadParams()
l, c = p.arm, p.k_torque

M = np.array([
    [ 1.0,  1.0,  1.0,  1.0],
    [  -l,   -l,    l,    l],
    [   l,   -l,   -l,    l],
    [  -c,    c,   -c,    c],
])
assert np.allclose(M, p.mixer_matrix())

M_inv = np.linalg.inv(M)
assert np.allclose(M_inv, p.allocation_matrix())

u_hover = np.array([p.weight, 0.0, 0.0, 0.0])
f_hover = M_inv @ u_hover
print("hover motor thrusts:", f_hover.round(4))
assert np.allclose(f_hover, p.weight / 4)            # four equal = mg/4

f = wrench_to_motor_forces(u_hover, p)
assert np.allclose(motor_forces_to_wrench(f, p), u_hover)
print("round-trip OK; hover = mg/4 per motor")

5 · Going further (optional)

  • Pure-roll command. Send \(\mathbf{u}=[mg, 0.05, 0, 0]\). Which motors increase, which decrease? Confirm all four change (the X-frame signature).
  • Yaw split. Send a small \(\tau_z\) only. Verify the CW pair and CCW pair split in opposite directions while \(T\) stays \(mg\).
