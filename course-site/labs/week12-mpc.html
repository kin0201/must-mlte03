1 · The 5-minute recap

MPC is receding-horizon control: at each step we predict \(N\) steps ahead, optimize a quadratic cost over the planned input sequence subject to input limits, apply only the first move, then re-solve at the next step. Working in deviations from the hover equilibrium, the discretized model is

\[ \delta\mathbf{x}_{k+1} = A_d\,\delta\mathbf{x}_k + B_d\,\delta\mathbf{u}_k,\qquad A_d = I + A\,\Delta t,\ \ B_d = B\,\Delta t \]

Stacking the horizon condenses the prediction so the only decision variable is the input sequence \( \mathbf{U} \):

\[ \mathbf{X} = S_x\,\delta\mathbf{x}_0 + S_u\,\mathbf{U},\qquad J(\mathbf{U}) = \mathbf{U}^\top H\,\mathbf{U} + 2\,\mathbf{g}^\top\mathbf{U} \]

The terminal cost uses the LQR Riccati matrix \(P=\)care(A,B,Q,R) (the infinite-horizon tail), and each \( \delta\mathbf{u}_k \) is held inside a box \( \mathbf{u}_{\text{lo}}\le\delta\mathbf{u}_k\le\mathbf{u}_{\text{hi}} \). That box is the whole point: where Week-7 LQR clips when it hits a limit, MPC plans a feasible path to the target.

Conventions (don't trip on these) All math follows CONVENTIONS.md: z-up / ENU (gravity \(-z\), thrust \(+\)body-\(z\)), intrinsic ZYX Euler, wrench \( \mathbf{u}=[T,\tau_x,\tau_y,\tau_z] \). The simulator's mixer is X-frame (every motor contributes to roll and pitch) — not plus-frame. You return / configure a wrench; the simulator does the mixing and clips each motor to \([f_{\min},f_{\max}]\).

3 · Set up the constrained step track

Work through the steps. You will build a tiny script that commands a step setpoint, caps the available thrust, and checks that the motors never exceed f_max. Recall the state layout: x[0:3] position, x[3:6] velocity, x[6:9] Euler \((\phi,\theta,\psi)\), x[9:12] body rates \((p,q,r)\).

1 Build the model & a step reference imports

Use the shared step trajectory generator: hold start, then jump to position at t_step. We climb from \(z=1.0\) to \(z=3.0\):

import numpy as np
from quadsim import Simulator, QuadParams
from quadsim.dynamics import hover_state
from quadsim.controllers import LinearMPC
from quadsim import trajectories as traj

p   = QuadParams()
sim = Simulator(p)
climb = traj.step(position=[0, 0, 3.0], start=(0, 0, 1.0), t_step=0.5)
2 Instantiate LinearMPC — note the horizon configure

The defaults give horizon \(N=25\) at \(\Delta t=0.05\,\)s — a 1.25 s look-ahead — with the Week-7 LQR weights \((Q,R)\) and the terminal Riccati \(P\) built for you in __init__:

mpc = LinearMPC(p)                 # N=25, dt_mpc=0.05  -> 1.25 s horizon

You don't touch \(H\), \(S_x\), \(S_u\) or \(P\) — they're assembled once at construction. Your job is to choose the constraint next.

3 Cap the thrust so the box bites the core

By default the input box uses the full motor envelope, so the limit rarely activates. Pass dT_max to allow only a small thrust margin above hover — now the constraint is binding and you can see MPC plan around it:

mpc_tight = LinearMPC(p, dT_max=1.0)   # only +1.0 N above hover trim allowed

Internally this sets the upper bound on the thrust-deviation entry of every \( \delta\mathbf{u}_k \) in the box \( \mathbf{u}_{\text{lo}}\le\delta\mathbf{u}_k\le\mathbf{u}_{\text{hi}} \). The torque bounds stay at \( \pm\,l\,f_{\max} \).

4 Run the closed loop simulate

Hand the controller and the step reference to the simulator. MPC re-solves its QP every step from the freshly measured state — that's the feedback:

x0  = hover_state(position=(0, 0, 1.0))
log = sim.run(x0, mpc_tight, reference=climb, t_final=10.0)
5 Check the limit was respected verify

The graded fact: the quad reaches the setpoint and no motor ever exceeds f_max. The per-motor thrusts are logged in log.f:

final_z = log.position[-1, 2]
max_f   = log.f.max()
ok      = max_f <= p.f_max + 1e-6
print(f"final z = {final_z:.2f} m  (target 3.0)")
print(f"max motor = {max_f:.2f} N  (limit {p.f_max})  -> "
      f"{'within limits' if ok else 'VIOLATED'}")

# examples/wk12_mpc.py — Week 12 checkpoint: constrained step track
import numpy as np
from quadsim import Simulator, QuadParams
from quadsim.dynamics import hover_state
from quadsim.controllers import LinearMPC
from quadsim import trajectories as traj

p   = QuadParams()
sim = Simulator(p)
climb = traj.step(position=[0, 0, 3.0], start=(0, 0, 1.0), t_step=0.5)

# only a small thrust margin above hover -> the input box is binding
mpc = LinearMPC(p, dT_max=1.0)

x0  = hover_state(position=(0, 0, 1.0))
log = sim.run(x0, mpc, reference=climb, t_final=10.0)

final_z = log.position[-1, 2]
max_f   = log.f.max()
ok      = max_f <= p.f_max + 1e-6
print(f"final z = {final_z:.2f} m  (target 3.0)")
print(f"max motor = {max_f:.2f} N  (limit {p.f_max})  -> "
      f"{'within limits' if ok else 'VIOLATED'}")

from quadsim import plotting as viz
viz.plot_states(log, save="wk12_mpc.png", show=False)
print("saved wk12_mpc.png")

Expected — your graded checkpoint ⭐
  • Reaches the target: final \(z \approx 3.0\,\)m (it climbs all the way despite the tight thrust cap).
  • Respects the limit: max motor is \( \le f_{\max} \) — prints within limits, never VIOLATED.
  • Plans, not clips: the climb is smooth — MPC spreads the limited thrust over the horizon rather than slamming and saturating.

5 · Going further (optional)

  • Loosen the cap. Re-run with dT_max \(\in \{0.5, 1.0, 3.0\}\). How does the climb time change as the box opens up?
  • Shrink the horizon. Pass horizon=5 vs horizon=25. With the terminal Riccati \(P\) in place, how short can \(N\) get before tracking degrades? (This is what \(P\) buys you.)
  • Drop the terminal weight (thought experiment). Argue what would happen to stability for small \(N\) if the last block of \( \bar Q \) were just \(Q\) instead of \(P\).
  • Preview teaser. Pass ref_fn=climb so MPC previews the setpoint along the horizon. Note any change — this is next week's feedforward story.

6 · This controller is the first draft of your final project

The final project is individual: you build, certify and defend your own controller. The same LinearMPC you configured above, pointed at mission M3, is where it starts.

Every student certifies against a different quadcopter certify.py --student <your ID> derives your vehicle's mass, arm length, \(k_\tau\) and inertia deterministically from your student ID — the same ID always gives the same aircraft, on any machine. Discuss theory freely and read each other's code freely, but a controller tuned to close REQ-M3-1 on a classmate's vehicle will not simply pass on yours. Record your student ID in your README; a run made with the wrong ID is a run on somebody else's aircraft and does not count.

See your own numbers, and take the first certification run, before Week 13:

python -m quadsim.student_params <your ID>
python certify.py --controller quadsim.controllers.cascade_pid:CascadePID \
       --student <your ID> --mission M3     # your frozen baseline — expect a red REQ-M3-1
python certify.py --controller <your.mpc:Class> --student <your ID> --mission M3
Baseline freeze — today's project gate Run CascadePID on M3 with your student ID, seed 0 plus four others; write baseline.json (metric values, seeds, student ID, git hash, aircraft params, date); commit the metrics script and the baseline file together and tag baseline-v1. After that the numbers change only with a signed note in your decision log. On the course-default vehicle (no --student) the reference numbers are 0.540 m (CascadePID, FAIL) and 0.473 m (LinearMPC, PASS) — yours will differ, the pattern will not.
